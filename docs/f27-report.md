# F27 Report — Appointment & Booking Vertical Slice

## 1. Executive summary

F27 implements Appointments and Booking end-to-end in Na Pista and Na Pista Console, following ADR-042/043/044
without reopening them. Backend: `appointments` table with three tenant-safe composite FKs, lifecycle CHECKs, and
the **PostgreSQL exclusion constraint** `appointments_professional_no_overlap` (`btree_gist`, `tstzrange(start_at,
end_at, '[)')`, partial on `status <> 'CANCELED'`), live on the database; booking, bookable slots, listing,
rescheduling, cancellation, completion, permissions, entitlement, transactional audit, post-commit usage, error
mapping. Console: day view, guided create flow on server-computed bookable slots, detail with reschedule/cancel/
complete/notes, Professional and Customer integrations. UL Platform: **no production change** (two dev-only fixture
scripts, the F19–F26 convention).

Concurrency was proven with real simultaneous writes, including a live proof that a second writer **blocks** on
the first's uncommitted overlapping row and then fails. Testing also surfaced one real defect, fixed and documented
(§17): under a tight race PostgreSQL can resolve two overlapping writers with `40P01 deadlock_detected` instead of
`23P01`; the invariant was never violated, but the loser got a 500 — it now gets `409 APPOINTMENT_CONFLICT`.

Full F20–F27 regression: **203 unit + 177 integration + 211 E2E = 591 tests, all passing**; Console 80/80.
**Status: COMPLETE.**

## 2. F27A decisions implemented

ADR-042 (model), ADR-043 (lifecycle), ADR-044 (concurrency) — implemented as decided; all three now marked
"implemented". Frozen brief decisions honoured: STAFF read-only; 365-day horizon; no completion before `start_at`;
exactly one Customer/Professional/Service; `[start_at, end_at)`; `timestamptz`; duration frozen; name/price/currency
snapshotted; Customer immutable; ACTIVE Professional/Service required; SCHEDULED → COMPLETED | CANCELED, both
terminal; no NO_SHOW; canceled does not block; exclusion constraint; 409 APPOINTMENT_CONFLICT; availability advisory,
write authoritative; F26 engine reused, not duplicated, not called over HTTP; `catalog.enabled`; `api_requests` after
commit; no Platform production change.

Refinements (recorded in the ADRs' "Implementation note", no semantic change):
1. **Error codes from the F27 brief adopted where more specific than the ADR's generic ones**:
   `APPOINTMENT_COMPLETION_TOO_EARLY` (409) instead of `INVALID_APPOINTMENT_STATE` for "complete before start";
   `BOOKING_HORIZON_EXCEEDED` (400) instead of `VALIDATION_ERROR` for "beyond 365 days". Same statuses and rules.
2. **Not adopted**: `PROFESSIONAL_SERVICE_NOT_FOUND`. The brief says "do not invent duplicate codes if equivalent
   codes already exist": F26 already answers "not associated" with `404 NOT_FOUND` (deliberately not distinguishing
   it), and ADR-042 froze the same — reused unchanged.
3. **40P01 mapping** (§17) — an amendment to ADR-044's mapping table, found by testing, documented in ADR-044.

No contradiction with an ADR required stopping an implementation path.

## 4. Database schema

`na_pista.appointments` (`src/db/schema/appointments.ts`): `id`, `organization_id`, `customer_id`, `professional_id`,
`service_id` (all NOT NULL), `start_at`, `end_at` (`timestamptz` NOT NULL), `status` (default `SCHEDULED`),
`service_name`, `service_price numeric(14,2) NULL`, `currency`, `notes`, `cancellation_reason`, `canceled_at`,
`completed_at`, `created_at`, `updated_at` — exactly ADR-042's field set (no `duration_minutes`, no name snapshots of
Customer/Professional, no metadata JSON, no override fields).

Constraints: composite FKs `appointments_{customer,professional,service}_org_fk` → the existing `*_org_id_unique`
targets; CHECKs `end_after_start`, `status_valid`, `canceled_at_matches_status`, `completed_at_matches_status`,
`cancellation_reason_only_when_canceled`, `service_price_non_negative`, `currency_shape`; exclusion constraint (§16).
Indexes: `(org, start_at)`, `(org, professional_id, start_at)`, `(org, customer_id, start_at)` + the constraint's GiST.

## 6. btree_gist

- **Why**: supplies GiST equality operator classes for `uuid`, so tenant + professional keys and the time range sit
  in one exclusion constraint.
- **Where**: `extensions` schema (Supabase convention), version 1.7, installed by Na Pista migration `0008` — Na
  Pista owns it.
- **Shared database**: per OD-16 the physical PostgreSQL database is shared with UL Platform (separate schemas). An
  extension is a database-level object; it is inert unless used. Verified after installation: **no index outside
  `na_pista` uses a `btree_gist` operator class** (catalog query returned 0) — no Platform-side dependency exists or
  was created. No UL Platform table, schema, migration or code changed; UL Platform's own test fixtures ran against it
  unchanged (§32).

## 7. Appointment model

One staff-committed reservation of one Professional's time, for one Service, for one Na Pista business Customer,
over one absolute half-open interval. API representation = the row + derived `durationMinutes` (`end − start`).

## 8. Customer semantics

Required; the Na Pista business Customer (never a Platform User); composite FK; must be ACTIVE to book or
reschedule (`409 CUSTOMER_ARCHIVED`); immutable after booking (`customerId` is not accepted by PATCH — 400); no
name/email/phone snapshot; archived Customer's appointments remain and can still be canceled/completed.

## 9. Professional semantics

Required; composite FK; ACTIVE required for booking and as the reschedule target (`409 PROFESSIONAL_ARCHIVED`).
Archiving never deletes, cancels or migrates appointments; reschedule may move an appointment to another ACTIVE
Professional associated with the booked Service.

## 10. Service semantics

Required; composite FK; ACTIVE required for booking and rescheduling (`409 SERVICE_ARCHIVED`); must be associated
with the Professional through `professional_services`, read live (no new join table). `serviceId` immutable.
Service schema untouched.

## 11. Snapshot semantics

`service_name`, `service_price` (NULL stays NULL — unpriced Services are bookable), `currency` (from
`src/shared/money.ts`, the single constant now shared with Orders) captured once at creation
(`buildBookingSnapshot`); never re-captured on reschedule; proven unchanged after renaming, repricing and re-timing
the Service.

## 12. Time semantics

- `timestamptz` instants; API input requires `Z` or an explicit offset and whole minutes; output is UTC ISO.
- `src/modules/appointments/time.ts` — the single conversion module, built-in `Intl` only: `toLocal`
  (UTC→org-local, unambiguous) and `localToInstant` (org-local→UTC, ADR-040 DST contract: gap → `null`/skip,
  ambiguous → first occurrence; `gap: "forward"` only for day-window boundaries). The timezone always comes from
  `organization_settings`; never server/browser/UTC/hardcoded; unknown timezone throws.
- Missing timezone → `409 TIMEZONE_NOT_CONFIGURED` on create, reschedule, list and bookable slots.
- **Horizon**: absolute and inclusive — `now ≤ startAt ≤ now + 365×24h` (server clock), applied to create and
  reschedule. Instant-based, so no offset spelling can move a start across a bound (unit-tested with a `+14:00`
  spelling of the exact limit).
- **Time source**: the server clock (`new Date()`) for horizon and completion; never client-supplied. Service
  functions accept an optional `now` used only by tests for determinism (routes never pass it).
- DST is now genuinely exercised (Europe/Lisbon gap/overlap unit tests); Luanda has no DST.

## 13. Lifecycle

`lifecycle.ts` (pure): `assertTransition` — only SCHEDULED accepts `reschedule`/`update`/`cancel`/`complete`;
`complete` needs `now ≥ start_at`. Terminal states reject everything (`409 INVALID_APPOINTMENT_STATE`). No DRAFT,
CONFIRMED, NO_SHOW or hidden states; DB CHECK restricts `status` to the three values.

## 14. Booking flow

Before the transaction: Zod (strict), booking window, timezone. One READ COMMITTED transaction: Customer ACTIVE →
Professional ACTIVE → Service ACTIVE → association → F26 availability for the local date → INSERT with snapshots
(conflicts mapped, §17) → audit `appointment.created`. After commit only: `recordUsage` (`api_requests`). No HTTP
call and no slow external call inside the transaction; availability is pure in-memory computation over rows read in
the transaction.

## 15. Availability integration

`booking.ts` reuses F26's `computeAvailability` unchanged for ONE local date and the booked duration;
`isWithinAvailability` requires the local start time ∈ `serviceStartTimes` (encodes working day, exception
precedence, 15-minute grid anchored at interval start, duration fit). Schedule rows are read through F26's own
`listScheduleRules`/`listScheduleExceptionsInRange` (executor-aware). `getAvailabilityOrThrow` is not called; F26 is
not called over HTTP; no scheduling file changed. **Bookable slots** (`computeBookableSlots`) = F26 start times →
instants (DST gap skipped) − slots overlapping non-canceled appointments − slots outside the booking window; never
persisted. Outside availability → `409 APPOINTMENT_OUTSIDE_AVAILABILITY`, no override (the Scheduling-exception
workaround is proven by an integration test).

## 16. Conflict enforcement

```sql
ALTER TABLE "na_pista"."appointments" ADD CONSTRAINT "appointments_professional_no_overlap"
  EXCLUDE USING gist ("organization_id" WITH =, "professional_id" WITH =,
                      tstzrange("start_at", "end_at", '[)') WITH &&)
  WHERE ("status" <> 'CANCELED');
```

1. **Interval semantics**: `[start, end)` — adjacent appointments allowed, partial/identical overlaps rejected.
2. **Canceled predicate**: `status <> 'CANCELED'` — canceled rows release their interval; any future state blocks by
   default; un-canceling into an occupied interval is rejected by PostgreSQL itself (raw-UPDATE test).
3. **Scoping**: `organization_id` and `professional_id` equality — other tenants and other Professionals never
   conflict.
4. **PostgreSQL behaviour**: enforced on every INSERT and every UPDATE producing a new row version, by every writer;
   a writer that meets a concurrent uncommitted overlapping row waits for that transaction and fails if it commits /
   proceeds if it rolls back — both branches proven live (§31).
5. **Authority**: the application never pre-checks conflicts with a SELECT; the constraint is the only conflict
   authority.

## 17. Concurrency

- **Row lock** (`getAppointmentForUpdate`, `SELECT … FOR UPDATE`) on every mutation of an existing appointment
  (reschedule, notes, cancel, complete) — concurrent operations on the SAME appointment serialize and the loser
  sees the real state. The exclusion constraint protects overlap ACROSS appointments. Both are needed.
- **Error mapping** (`mapBookingWriteError`, applied only to the guarded INSERT/UPDATE): `23P01` on
  `appointments_professional_no_overlap` → `409 APPOINTMENT_CONFLICT`; **`40P01` → `409 APPOINTMENT_CONFLICT`**
  (below); anything else untouched. `errorHandler` additionally maps any untranslated `23P01` to a generic
  `409 CONFLICT`. Responses never contain constraint names, SQL or driver text (asserted in unit, integration, E2E).
- **Finding — deadlocks under tight races.** The first full E2E run had one failure: in a 5-way simultaneous booking
  exactly one request won (invariant intact) but the 4 losers returned HTTP 500 instead of 409, their server-log
  timestamps ~1 s apart (= `deadlock_timeout`). The logged error lacked its cause, so `errorHandler` now also logs
  the SQLSTATE (server log only). Investigation: 320 raw single-statement racing INSERTs → only `23P01`, no
  deadlock; 125 racing writers through the real service transaction → **1× `40P01 deadlock detected`** on the
  appointments INSERT. Cause: an exclusion constraint inserts its index entry before checking, so two overlapping
  writers can wait on each other; PostgreSQL aborts one. The guarded statement can only wait on overlapping rows of
  the same Professional (FK `KEY SHARE` locks never block other inserters), so a deadlock there *is* a lost booking
  race → mapped to the same 409, still one attempt, no retry (ADR-044 unchanged in mechanism, amended in its mapping
  table). Regression: a deterministic mapping test + a 20-round × 5-writer stress test (100 racing writers, every
  loser must be `AppointmentConflictError`).
- **No retry loops** anywhere.

## 18. Rescheduling

`PATCH` with `startAt` and/or `professionalId` = in-place reschedule of the SAME row (identity, Customer, Service,
snapshots preserved; duration preserved from `end − start`, never re-read from the Service — proven after changing
the Service duration). Full revalidation: window, timezone, Customer ACTIVE, target Professional ACTIVE, Service
ACTIVE, association, F26 availability with the preserved duration, then the constrained UPDATE. Moving into its own
previous interval is fine (the old row version is not a conflict — tested). Audit `appointment.rescheduled`
(`from`/`to`), usage recorded. `notes` alone = `appointment.updated` (note text never copied to audit), no usage.
`status`/`customerId`/`serviceId`/`endAt` rejected by the strict schema (400). A PATCH that changes nothing is a
no-op without audit.

## 19. Cancellation

`POST …/cancel {reason?}` (1–500 chars): SCHEDULED → CANCELED only, `canceled_at` set, interval released
immediately, irreversible; allowed regardless of later archival. Audit `appointment.canceled` (`fromStatus`,
`hasReason`), usage recorded.

## 20. Completion

`POST …/complete`: SCHEDULED → COMPLETED only when the server clock ≥ `start_at` (else `409
APPOINTMENT_COMPLETION_TOO_EARLY`); `completed_at` set; terminal; keeps blocking its interval (proven). Audit
`appointment.completed`, usage recorded. No NO_SHOW.

## 21. Permissions

`appointments.read/create/update` in `authorization/permissions.ts` (and the Console's UX mirror): OWNER/ADMIN/
MANAGER all three; STAFF read only; no `appointments.delete`. `update` covers reschedule, notes, cancel, complete
(the `orders.update` precedent). Server-side via `requireAuthorized`; service credentials use `catalog.read`/
`catalog.write`. Proven E2E: STAFF 200 on reads, 403 on create/reschedule/notes/cancel/complete; MANAGER allowed;
`catalog.write` credential allowed; `usage.write`-only credential 403; no token 401.

## 22. Entitlement

`catalog.enabled` via the existing `requireCapability` on every route; no new Platform entitlement. E2E: unsubscribed
org → 503 without a credential, `403 ENTITLEMENT_REQUIRED` with one (read and write); subscribed org → 200.

## 23. Audit

`appointment.created`, `appointment.rescheduled`, `appointment.updated`, `appointment.canceled`,
`appointment.completed` — written inside the mutation's transaction (`recordAuditEvent(entry, tx)`); proven: a
failing audit insert rolls back the appointment insert; a conflicting loser leaves no audit row; reads/bookable slots
produce no audit.

## 24. Usage

Existing `recordUsage` → `api_requests`, called only after the transaction returns (commit): create, reschedule,
cancel, complete. Not for notes-only edits (Order precedent) or reads. Proven: integration counts `recordUsage` calls
(1 for a committed booking, 0 for conflict/validation/too-early failures); E2E reads the real Platform meter (+1 after
a committed booking, unchanged after a conflicting one).

## 27. Tenant isolation

HTTP (tenant context from membership/credential; foreign org path → 403; foreign ids on own path → 404), repository
(`assertTenant` + `organization_id` on every query), database (three composite FKs — raw cross-tenant inserts rejected
with the FK named; exclusion constraint keyed on `organization_id`). Proven: org A cannot book with org B's Customer/
Professional/Service, nor get/list/reschedule/edit/cancel/complete org B's appointment, nor read its bookable slots;
cross-org same-interval bookings both succeed; an org-A credential cannot operate on org B.

## 28. Security

Tenant isolation (above); authorization server-side on every route; human JWT and service credential paths both
tested; entitlement fail-closed; SQL only through Drizzle parameterization (the one `sql` template binds ISO strings
as parameters); raw DB errors never returned (mapped or generic 500 without details; SQLSTATE only in server logs);
no secrets in code or logs; date-range abuse bounded (31-day list, single-date slots, 365-day horizon, whole-minute
instants, no past starts); conflict bypass impossible (DB constraint on every write path, including raw SQL — tested);
direct status mutation impossible (strict PATCH schema; dedicated transitions; DB CHECKs); archived-resource bypass
closed on create and reschedule.

## 29. Performance

List by window uses `(org, start_at)`; professional/customer filters use their composite indexes; service/status
filters apply within the bounded window (no dedicated index — low value). The constraint check is a GiST index probe
per write. Bookable slots: one schedule read + one occupying-appointments query served by the constraint's own GiST
index (confirmed `Index Scan using …_no_overlap` in F27A) + pure in-memory computation for one date. No caching, no
slot table, no materialization. Observed latency is dominated by the remote Supabase pooler round-trips.

## 33. Limitations

- Bookable slots use the Service's *current* duration; when rescheduling an appointment whose Service duration has
  since changed, offered slots may not match its frozen duration (the server validates with the frozen duration and
  answers 409 if it does not fit).
- The appointment's own interval is subtracted from bookable slots during its own reschedule, so "shift by 15
  minutes" slots overlapping itself are not offered (the API accepts such a move — tested).
- A retry after a lost `201` gets `409 APPOINTMENT_CONFLICT`, not the original resource (no idempotency — see
  `docs/api/appointments-api.md` §Idempotency for the precise distinction).
- On a DST fall-back day, wall-clock end may differ from local start + duration by the shift (absolute duration exact).
- Names in lists are resolved live per unique customer (one GET each) — fine for daily volumes, not for bulk exports.
- List pagination is limit-only (≤ 500 within ≤ 31 days), the existing convention.
- A `40P01` mapped to conflict could, in a pathological multi-failure race, report a conflict for a slot that ends up
  free; the client's refresh shows it free again.
